# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Read first

`AGENTS.md` holds the binding project rules (domain invariants, test-first, no auto-commits). Start at `docs/README.md`. **Where the project is and what to work on is only in `docs/status.md`** (its Now / Next box); `docs/roadmap.md` holds the approved design of the current item; `docs/decisions.md` holds the locked decisions (never reopen them without the owner) and every later decision; `docs/way-of-work.md` is the process (design and approval, plan, Sonnet prompts, review, commit, deploy) and the list of docs each finished item updates. `docs/history/` is reference only. Work one step at a time and stop for review after each.

## Commands

Local Postgres (from repo root): `docker compose up -d --wait` (port 55432). Settings live in a gitignored `.env` at the repo root: create it once with `cp .env.example .env`. The Go commands (`cmd/api`, `cmd/db`, `cmd/testserver`), the Go database tests (through `internal/dotenv`), and Playwright load it automatically; a variable already set in the environment wins. Don't `export` the variables; put new settings in `.env` and document them in `.env.example`.

Backend (`backend/`):

```sh
go run ./cmd/db migrate      # repeatable
go run ./cmd/db init         # empty installed root, safe to repeat (production start: migrate, then init)
go run ./cmd/db seed         # only on an empty DB; refuses to overwrite (-fixture acceptance|campus|empty)
go run ./cmd/api             # :8080 (HTTP_ADDR to change); needs APP_ENV=dev|test|prod (in .env)
go test -race ./...
go vet ./...
go test ./internal/pathfinding -run TestName   # single test
```

Without `TEST_DATABASE_URL`, PostgreSQL tests skip. A green run with skipped DB tests does not verify migrations or round trips. DB tests use unique schemas and drop them afterward.

Frontend (`frontend/`):

```sh
npm ci
npm run dev                  # http://127.0.0.1:5174, proxies /api to :8080 (API_PROXY_TARGET)
npm test                     # vitest
npx vitest run src/features/pathfinding/projection.test.ts -t "name"   # single test
npm run typecheck
npm run build                # tsc --noEmit + vite build
npm run format:check         # prettier; `npm run format` to fix
npm run test:e2e:remote      # the same on the test machine (E2E_REMOTE in .env; 8 lanes, ~3.5 min); `-- e2e/x.spec.ts` for one file
npm run test:e2e             # Playwright (project `main`, then `recording`: specs named *.recording.spec.ts record plans and make drafts stale, so they run last); `npx playwright test e2e/planning.spec.ts` for one file
```

`go run ./cmd/testserver -fixture campus` and `go run ./cmd/db seed -fixture campus` use the generated campus fixture (development only); `SCALE=1 npx playwright test -c playwright.scale.config.ts` runs the opt-in scale spec against it. Playwright runs 4 workers, each on its own **lane**: its own `backend/cmd/testserver` (isolated schema, migrate+acceptance seed plus an "Expansion" draft, cleaned on shutdown) on 18090+N and its own Vite on 5180+N, so lanes never share data and it all runs alongside dev; `E2E_WORKERS` changes the count. Specs import `test`/`expect` from `e2e/fixtures.ts` (it points each worker at its lane), never from `@playwright/test`. Before handoff, run Go tests, frontend tests, typecheck, and build.

When `api/openapi.yaml` changes, lint it from `frontend/` with `npx --yes @redocly/cli lint ../api/openapi.yaml --extends minimal`.

## Architecture

Data flow: PostgreSQL → `persistence` loads a `topology.Snapshot` (installed, or installed + plan overlay) → pure domain packages operate on the snapshot → `httpapi` serializes. The frontend fetches via `src/shared/api.ts` (TanStack Query) and projects results onto React Flow.

- `internal/topology`: domain types (`Snapshot` of equipment, endpoints, links with context/revision) and `Validate`. Roles are explicit fields (`access`, `aggregation`, `backbone`, `passive`, and `none` for a `rack_item`, which has no endpoints and never enters traversal). Never infer roles from names.
- `internal/pathfinding`: pure BFS over physical continuity only. Edges are external cables plus internal front/rear bridges at the same position. Sibling ports on a device never create edges. It has no dependencies on HTTP, storage, or canvas.
- `internal/fixes`: pure direct fixes of installed names and details (`Apply`; `ApplyMany` for many details fixes at once, validating once at the end), used by `persistence.Store.Fix` and `Store.FixMany`; never topology, never the revision.
- `internal/planning`: plans are revisioned overlays. `Apply(base, plan)` produces a proposed snapshot without mutating installed; a plan is overlay v2: container additions, equipment additions, placements (IDs only; the old full-equipment `updates` are still read), renames of the equipment the plan adds, removals (equipment cascades to its endpoints, bridges and cables; a rack, node or site only when empty) and cable additions. `Check` collects every change that does not apply, keyed `<kind>:<id>`. `Execute` applies commands (`add_equipment`, `add_hdf`, `add_cable`, `move_equipment`, `add_site|node|rack`, `rename_equipment`, `delete_equipment|rack|node|site`, `disconnect_cable`, `remove_change`) with named-error occupancy/cable validation; `remove_change` is the one command allowed on a stale draft. `Diff` compares installed and proposed by ID for recording, and `Plan.Labels` keeps object names so drafts and recorded plans read in names. Installed topology, proposed topology, and visual layout are separate models.
- `internal/persistence`: pgx repositories with transaction discipline and draft/base revision conflict checks. `Record` (installed `FOR UPDATE`, then the plan) writes the Diff in a foreign-key-safe order, fills `plan_objects` and the labels, and sets a new installed revision; `Rebase` is Update draft. `httpapi.Repository` is the interface boundary, so HTTP tests can use fakes.
- `migrations/`: embedded and checksummed SQL. Append new files and never edit applied ones; the runner rejects changed checksums. Startup never migrates or seeds automatically.
- `internal/acceptance`: the fictional acceptance fixture (`docs/acceptance-example.md`) used by `cmd/db seed` and `cmd/testserver`. `internal/sample`: the older prototype fixture, now only for Go characterization tests. Neither is real inventory.
- Frontend look (D33): `src/shared/theme.css` holds every colour, font and size and the shared classes (`.btn`, `.chip`, `.field`, `.seg`, `.drawer`, `.tape`); feature CSS uses only `var(--…)`, guarded by `theme.test.ts`. `src/shared/ui/` has `Name` (bdi), `PlacePath`, `Pieces`, `Chip` and `Field`; `src/shared/textPieces.ts` has `TextPiece`, `piecesText` and `optionText` (an option cannot hold markup). Never join names into one string for display. `src/shared/equipment.ts` has `kindLabel`, `hasPorts` (false only for a rack item: check it before drawing a face or a port table) and `isPassiveEquipment` (panel or HDF; a rack item is neither active nor passive); `src/shared/rackItems.ts` has the rack item types, their labels, `rackItemPieces`, the default heights and `suggestedRackItemName`.
- Frontend: `src/app/App.tsx` is a large shell (header, drawers, Trace drawer, wiring); put new UI in feature-scoped folders under `src/features/`, not in `App.tsx`. `src/features/map/` is the conceptual map (D39, D40): one view, the **tree** of one network, left to right (BBs, frames of AGGs, node cards, all from real cables), with a selection and a drawer; there is no Focus view. Pure, unit-tested modules: `walks` (`equipmentWalks` over `followPort`: every walk from a device's endpoints with the passives passed, `WalkStep` with its jack), `hierarchy` (`buildHierarchies(index, installed?)`: every network's levels, AGG groups, node cards, tier lines, uplink marks and the up-graph `ups`, once per snapshot; Inventory's Problems reads the same marks), `hierarchyLayout` (boxes, frames, labels, `selectionBoxes`; Only problems), `hierarchyFlow` (`projectHierarchy`, `highlightedCards`, `hotCards`, `emphasisMarks`), `hierarchyFit`, `hierarchySelection` (`Selection`, `litBy`, `dependents`: what a selection lights, dims and cuts off, computed per selection from `ups`), `hierarchyDetails` (the drawer's rows: `nodeRows`, `switchWalks`, `wayUp`, `cables`, `passiveSentence`), `circuitNetwork`, `facets` (only `endpointLookup`, `facetKey`, `facetLabel`, used by the inspector, Physical and Explore), `networks`, `networkColors` with the `NetworkBadge` component, `connections` (label matching), `highlight` (node/site highlight), `location`, `routeList`, `snapshotIndex`, `exportRoute` (header text, file names, capture size, and the lazy `html-to-image`/`jspdf` capture), `center` (fit options, `fitViewport`, `panToShow`, `panToShowFirstFit`), `cardRole`; thin components `ConceptualMap`, `HierarchyCanvas`, `HierarchyPanel`, `FrameCard`, `HierarchyNodeCard`, `TierCard`, `HierarchyDrawer` (with the `hierarchyActions` context), `MapControls`, `MapResults`; and `mapSession` as the session-only store: the shown network (`networks()`, `showNetwork(id)`, pure `shownNetworks`), Only problems, the open nodes, the selection (`selection()`, `select`, `clear`), the tree's viewport, the node/site highlight, the route view's on/off switch and the pending fit request (shared by Installed and Plan, never persisted). Show on map, from anywhere, is App's `showOnMap(id)`, the one entry point: it selects on the tree. The tree is laid out from the data and never dragged or saved; on Conceptual the header's network chooses it. Compute snapshot-only work once per snapshot (`indexSnapshot`, `buildHierarchies`) and keep selection and route work separate. Map lines are drawing aids and never feed traversal. Refetches reconcile by ID and never remount or refit; a selection pans but never refits. The route view is `paths/RouteDiagram` laid over the map; the map under it stays mounted and untouched. `features/inspector/` is the equipment inspector (`model` is pure; `Inspector`, `Overview`, `PortTable`); its Show on map selects the equipment on the tree. `features/physical/` is the physical explorer: pure, unit-tested modules (`location` with `resolveLocation` fallback, `history`, `inventory` (counts and route marks, once per snapshot), `connections`, `layout`, `elevation`, `faces`, `detail`, `explorerModel`, `equipmentModel`, `drops`) plus thin components (`PhysicalExplorer`, `SitesGrid`, `SiteCanvas`, `NodeLevel`, `RackElevation`, `EquipmentPage`), and `physicalSession` as the session-only store (location, Back history, per-site fit and viewport) outside the Workspace like `mapSession`. The site screen's node positions are saved on the server (`GET`/`PUT`/`DELETE` site layout, last write wins, saved once at drag stop, optimistic with rollback); lines between nodes are a summary of real cables and never feed traversal. Colors follow state, never the network ID. The explorer's root carries `data-*` marks that the specs assert. `features/paths/` explains a path: pure `follow` (`followPort` over stored links only, `walkOfRoute` for a server route), `sheet` (`buildSheet`, names kept apart as `{text} | {name}` pieces), `uplinks`, `diagram`, and thin `WalkSheet`, `UplinksSummary` (`useUplinks`: Find AGG / BB per access switch, its own query) and `RouteDiagram` (the route view). `features/details/` is the details UI: pure `model` (field specs, value lists, `changedFix`, history lines) and thin `DetailsEditor`, `EquipmentDetails`, `PortDetails`, `HistoryTab`; a direct fix calls App's `onFixed`, which refetches topology and history because the revision does not change. `features/networks/` is the Manage networks drawer (`model` is pure); networks can be created and renamed through the API, never deleted. `features/planning/` is the editing UI and the Changes drawer: pure modules (`deletePreview` with the cut-circuit walk, `summary` (the grouped change lines, names only), `changes`, `containers`, `goTo`, `rebaseSession`) and thin components (confirms, forms, `LibraryItems`, `ChangesDrawer`, `ReviewStep`, `StaleChanges`, `StaleCard`); every edit goes through one `PlanEdit` function that App provides only for a current draft (it also takes `batch` and `remove_change`). `features/patching/` is the patching screen (Connect… and Connect a range…): pure `patching.ts` (location tree, far default and side, next free, pair marks), `patchingSession` (open request, recent far targets, side per equipment; session-only), `LocationPicker` (Site › Node › Rack › Equipment), `PatchingScreen`, `ConnectPopover` (at a free jack in a plan) and `PatchingHost` (mounted once in the Workspace), and `useInlineDialog` gives every inline confirm and form Escape and focus return. `features/inventory/` is the Inventory view (D37, D38), the header's third choice: pure, unit-tested modules (`columns` (the six lists, columns, pills, groups; `missing` and `fits` are list-valued), `rows` (`buildRows`: one row per equipment, endpoint and cable with used/free, plus racks and problems, built once per snapshot), `racks`, `problems`, `workList` (a plan's Changes lines in work order with places), `query` (`applyQuery`: search, pills, sort, group, page), `csv`, `bulkEdit` (Edit details of many rows: counts, the direct-fix request, the plan batch), `manyPreview`, `labels`, `savedViews` (`localStorage`, try/catch), `model` (table items, the window, the meta line, group counts, the one-row and many-row commands and their batches)) and `inventorySession` (current list, each list's query and selection, hidden columns and the header's network; session-only); thin components `InventoryPage`, `InventoryTable` (windowed: only the rows on screen are drawn), `Cell`, `ValuePicker`, `Panes` (CSV, Edit columns), `BulkEditPane`, `ManyPanes` (Delete N…, Disconnect N…), `LabelsPane` with `exportLabels` (one captured page per sheet, like `exportRoute`) and `RowMenu`. Its actions call App's existing functions (inspector, Show on map, Physical, the inspector's confirms through `openRequest`); its root carries `data-inventory-*` marks that the specs assert. A stale draft is never drawn (a card replaces the map, Physical and the Inventory).

## Keeping things in sync

With each finished item, update `api/openapi.yaml` (current executable API only, not future features), `frontend/src/shared/types.ts`, `docs/status.md` and the other docs listed in `docs/way-of-work.md` ("Keeping the docs true"). Don't claim behavior that isn't runnable, and never write the same fact in two docs.
