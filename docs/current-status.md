## Implemented

### Domain and persistence (M1)

- **Networks and membership.** `topology.Network{ID, Name}` and `Snapshot.Networks`. Every `switch` has exactly one `networkId` that references an existing network; `panel` and `hdf` have none (they are shared). No default network exists anywhere. Networks are listed in the snapshot, in creation order, and since M4 can be **created and renamed** through the API (never deleted); see Networks below.
- **Roles.** `Validate` enforces role by kind: `switch` is `access`, `aggregation`, or `backbone`; `panel` and `hdf` are `passive`. Roles are never inferred from names.
- **HDF structure.** Equipment kind `hdf` with `topology.Subpanel{ID, EquipmentID, Row, Column}` (`Snapshot.Subpanels`). Rows are 1–32, columns A–D, six local positions per subpanel. `Endpoint.SubpanelID` (a stable ID) replaces the old free-text subpanel; labels are display text and are never parsed. `Validate` requires every HDF to have a complete grid: rows 1..N with all four columns, a front and rear endpoint at each of six positions per subpanel, and exactly one internal bridge per position. An N-row HDF therefore has 4N subpanels, 24N positions, and 48N side endpoints. Row count is derived from the stored subpanels and is independent of rack height (the equipment's own `height`).
- **Bridges and occupancy.** An internal bridge is valid only between opposite sides of the same position of the same subpanel (or the same standard-panel position). Endpoint identity and occupancy are scoped to the owning subpanel, so local numbering restarts per subpanel. Same-chassis external cables remain rejected. Cables between devices on different networks are accepted, not rejected; Find AGG / BB reports them as mismatches (below).
- **`add_hdf` plan command.** `{name, rackId, unit, height, rows}` creates the chassis, subpanels, positions, endpoints, and bridges in one revision using `topology.NewHDF`, the same builder the fixtures use. `rows` must be 1–32 (checked before anything is built, so a command creates at most 128 subpanels, 768 positions, and 1,536 side endpoints); `unit` and `height` must be 1–100 and fit the rack without overlapping installed or proposed equipment. Any validation, placement, or revision failure persists nothing and leaves the draft revision unchanged. `add_equipment` still creates only switches and standard panels (1–48 positions); it rejects kind `hdf`.
- **Plans.** `add_equipment` takes `networkId` (required for switches, rejected for panels) and accepts the `backbone` role. `planning.Plan` carries `Subpanels` in the same JSON document. Plans saved without a `subpanels` key (or `null`) are read as an empty list. A stored plan that contains an HDF chassis without its complete grid is refused as an overlay instead of being served half-valid.
- **Migrations 001–007** (embedded, checksummed, append-only; 005 and 006 are described under M4 below, 007 under M5a):
  - `003_networks.sql` creates `networks`, adds `equipment.network_id`, and requires it exactly for switches. Its preflight raises an error telling you to reset the development database and reseed if any switch exists, or any saved plan's `additions.equipment` array contains a switch, because no membership is known. It never assigns a default network.
  - `004_hdf_structure.sql` creates `subpanels`, adds `hdf` to the equipment kinds, and replaces `endpoints.subpanel` with a `subpanel_id` foreign key and an equivalent uniqueness rule. Its preflight raises the same kind of error if any installed endpoint or any saved plan endpoint has a non-empty legacy `subpanel` string. Empty strings are dropped and existing endpoint IDs are unchanged.
  - Both preflights run before anything is altered. A database that was seeded before M1 contains switches, so `migrate` refuses it: reset the development database and reseed (see the README).
- **Traversal:** pure physical BFS over external cables and same-position front/rear bridges; sibling device ports never create edges; HDF endpoints traverse like any other endpoint. Exact point-to-point is unchanged (identical endpoints give a zero-hop route; cable order carries no direction).
- Go `net/http` API, pgx repositories with the existing lock order (installed `FOR SHARE`, then draft `FOR UPDATE`), draft/base revision conflicts, atomic validation and rollback, consistent installed reads.

### Find AGG / BB (M2)

`distribution` mode of `POST /api/traces` replaces the removed `aggregation` mode, which now returns 422, so no path can silently drop BB results.

- **Starts.** `device` searches every port of one switch; `start` searches one exact device port, or one exact panel or HDF port. Exactly one of the two; `end` is rejected; a `device` must be a switch. Each starting endpoint is searched independently (BFS, each endpoint visited once, so loops terminate) and stops at the first active endpoint it reaches: no transit through sibling ports, including AGG to BB.
- **Destinations.** Endpoints of `aggregation` or `backbone` devices other than the starting device. The actual role is preserved (BB is never relabeled AGG); AGG routes are listed before BB; BB routes are retained when AGGs are reachable. AGG-15 (unconnected) is never a result.
- **Source network and mismatches.** A device or device-port start uses the device's network. A destination in that network is a **route**; one in another network is a **mismatch**, returned separately in `mismatches` and never as a route.
- **Passive starts.** A panel or HDF port searches from that exact port (hops are counted from it, including its own bridge), in both directions. Its source network is the network of the access device found on the same circuit, never the panel or a name. With no access device (or access devices on different networks) the source network is **unresolved**: every reached destination is a route carrying its own network, `sourceNetworkId` is omitted, and the start outcome is `unresolved_network`. HDF-01 3C/5 resolves Network A and reaches AGG-03; 3C/2 resolves Network B and reaches AGG-12.
- **Start outcomes** (`starts`, one per searched endpoint): `reached`, `mismatch`, `no_destination` (connected, but the circuit ends at a non-destination endpoint or a passive dead end), `disconnected` (the circuit has no external cable), `unresolved_network`.
- **Result.** Each route and mismatch carries `destinationEquipmentId`, `destinationRole`, `destinationNetworkId`, `sourceNetworkId`, and ordered `hops`. Routes sort by role (AGG first), start endpoint, then destination endpoint; mismatches by start then destination; `starts` by endpoint; input order never matters. `status` is `reached` when any route exists, otherwise `unreachable`, with a `reason` derived from the start outcomes ("from N of M searched port(s)" counts ports that produced a route).
- **Limit.** At most 1,000 routes plus mismatches (routes kept first). `truncated` is true only when results were dropped, and the reason says so; a limit is never reported as unreachable.
- **Location and HDF identity.** The response carries stable endpoint and equipment IDs only. Clients resolve rack, node, site, and HDF subpanel row/column, position, and side from the snapshot they already load; no duplicate location payload exists.
- **Deferred to M6, as recorded in the M3 plan:** focused equipment/neighborhood fetch and route-object fetch APIs. M3 and M3.1 load full snapshots and do highlight, route view, and summaries on the client; scoped contracts are designed against measured large-network data.

### Saved node layout and networks (M4)

Presentation and reference data only: none of these writes changes the topology revision or any saved plan, so no draft goes stale and no pinned trace conflicts.

- **Migration `005_site_layouts.sql`** creates `node_layouts(node_id PRIMARY KEY REFERENCES location_nodes ON DELETE CASCADE, x, y double precision NOT NULL, updated_at)`, with a range check of ±1,000,000 on both coordinates (NaN fails it too).
- **Migration `006_network_order.sql`** adds `networks.seq` (a creation order; existing networks are numbered in ID order, so their colors do not change) and a unique index on `lower(btrim(name))`. Its preflight refuses, with an error that names the colliding names, if two networks already collide ignoring case and surrounding spaces; it never renames anything and records nothing. Snapshots list networks by `seq`.
- **Layout endpoints.** `GET /api/sites/{siteId}/layout` returns `{siteId, positions: [{nodeId, x, y}]}` (only saved nodes, `[]` when none); `PUT /api/sites/{siteId}/layout/nodes/{nodeId}` with `{x, y}` upserts one node's position and returns it (**last write wins per node**, no revision check); `DELETE /api/sites/{siteId}/layout` removes that site's positions only (204, also when there are none). 404 for an unknown site; 422 when the node does not belong to the site, or a coordinate is missing, not a number, or outside ±1,000,000; unknown fields and malformed JSON 400.
- **Network endpoints.** `POST /api/networks` `{name}` returns `201 {id, name}` with a server-generated ID (`network-` plus a random suffix) that never changes; `PATCH /api/networks/{id}` `{name}` returns `200`. A name is trimmed and 1–64 characters (counted as characters, not bytes) and unique ignoring case: 422 for an empty or too long name, 409 for a duplicate, 404 for an unknown ID, 400 for unknown fields. Renaming changes only the display name (membership, circuits, drafts and the order are untouched). There is no delete.

### Editing and recording installed changes (M5a)

**Plan overlay v2** (`internal/planning`). A plan is a revisioned overlay with `sites`, `nodes` and `racks` (additions), `equipment` with its `subpanels`, `endpoints` and `links`, `placements` (`{equipmentId, rackId, unit}`, IDs only), `removals` (`{equipment, links, racks, nodes, sites}`, IDs of installed objects) and `labels`. Plans saved with the old full-equipment `updates` still load: each entry is read as a placement, and the next command folds them into `placements`. `Apply(base, plan)` runs base → container additions → equipment additions → placements → removals → cable additions → `Validate`, is all-or-nothing, and never mutates the base. A removed equipment takes its endpoints, bridges, subpanels and every cable on them; a rack, node or site can be removed only when empty after the plan. Removing something the plan itself added deletes the addition and records no removal. Installed IDs never change.

**`Check(base, plan)`** applies the changes in that order against the current installed topology (it ignores the revision) and returns every change that does not apply, as `{change, reason}` with `change` = `<kind>:<id>` (`add_site`, `add_node`, `add_rack`, `add_equipment`, `place_equipment`, `remove_cable`, `remove_equipment`, `remove_rack`, `remove_node`, `remove_site`, `add_cable`). It runs the changes in place and validates once; only when that fails does it binary-search the responsible change, so 200 placements plus one bad one on the campus fixture take about 65 ms.

**Plan commands** (`POST /api/plans/{id}/commands`, one payload per command, `expectedRevision` required; 400 malformed, 404 unknown plan or unknown `remove_change` key, 409 stale revision or a recorded plan, 422 invalid change; nothing is persisted on failure): `add_equipment`, `add_hdf`, `add_cable`, `move_equipment` (existing); `add_site {name}`, `add_node {siteId, name}`, `add_rack {nodeId, name, units 1–60}` (names unique among siblings, case-insensitive); `delete_equipment`, `disconnect_cable` (bridges refused), `delete_rack|node|site` (empty only), each with `target: {id}`; and `remove_change {change: {key}}`. Errors are written in names ("U4–6 in Rack SM01 is taken by HDF-01", "Rack SM01 has units 1–12; 3 units from U11 do not fit", "AGG-03 · Port 1 is already cabled (cable-a04)"); `Validate` stays the safety net. **`remove_change`** removes one change by its `Check` key and its structural dependents (an added equipment takes its plan cables and placement; an added rack takes its equipment and placements into it; a node its racks; a site its nodes), also undoes a removal or a disconnect, and is the **one command a stale draft accepts** (the post-change `Apply` is skipped there; on a current draft the result must still apply). It answers `{plan, removed: [keys]}`; every other command answers the bare plan.

**Labels.** `Plan.labels` maps an object ID to its name (equipment, racks, nodes, sites by name; an endpoint as "Equipment · label"; a removed cable as "A ↔ B"). Commands fill it for every object they add, remove, move or cable (both cable ends included), `remove_change` drops labels no change uses, and Record adds what Installed loses. It lets a stale draft say "PANEL-A · 10 · Front no longer exists" and a recorded plan name what it removed. Plans saved before labels load with an empty map.

**Check endpoint, Record and Update draft.**
- `POST /api/plans/{id}/check`: read-only, `{stale, conflicts: [{change, reason}]}` from `Check` against the current installed topology; a recorded plan is 409.
- `POST /api/plans/{id}/record {expectedRevision, note, recordedBy}`: locks installed `FOR UPDATE`, then the plan; requires a draft whose revision is `expectedRevision` and whose base is the installed revision (otherwise 409, "Installed changed since this draft; update the draft first" for a stale base); the note (1–500 characters) and `recordedBy` (1–100) are trimmed and required (422). It runs `Apply`, computes `planning.Diff(installed, proposed)` **by ID** (any other change to an existing object than an equipment's rack and unit is an error and rolls back), and writes in a foreign-key-safe order: deletes of links, occupancy, endpoints, subpanels and equipment; new sites, nodes and racks; placement moves (all occupancy rewritten after all updates, so swaps never collide); deletes of racks, nodes and sites; new equipment with occupancy, subpanels, endpoints and links. It fills `plan_objects` from the Diff (site, node, rack, equipment and cable rows, `added`, `moved` or `removed`; endpoints, subpanels and bridges are not listed), saves the labels, sets a new opaque installed revision (`rec-<UTC time>-<6 random characters>`), marks the plan `recorded` (`recordedAt`, `recordNote`, `recordedBy`) and bumps its revision. Everything is one transaction; the response is `{plan, installedRevision}`. Recording does not write `change_log`.
- `POST /api/plans/{id}/rebase {expectedRevision}` (Update draft): installed `FOR SHARE`, then the plan; a recorded plan or a wrong revision is 409; a draft already on the current base is returned unchanged; otherwise `Check` runs and, with no conflicts, the base moves to the current revision and the plan revision increases by one. With conflicts it answers 409 `{error, conflicts}` and changes nothing.
- A recorded plan refuses commands, record and rebase (409 "this plan is recorded and read-only"). `GET /api/plans` lists drafts and recorded plans; `GET /api/plans?objectId=<id>` lists only the recorded plans that changed that object, newest first (an empty `objectId` is 400).

**Migration `007_record_installed.sql`** adds `plans.status` (`draft`/`recorded`), `recorded_at`, `record_note` and `recorded_by`, with one check that ties them together (a draft has none; a recorded plan has a time, a note of 1–500 characters and a name of 1–100); creates `plan_objects(plan_id → plans ON DELETE CASCADE, object_kind, object_id, change)` with primary key `(plan_id, object_kind, object_id)` and an index on `(object_id, object_kind)` (History looks objects up by ID alone); and creates `change_log` with an index on `(entity_kind, entity_id, at)`. **`change_log` is not written by anything yet** (M5b direct fixes will).

**Editing UI** (`frontend/src/features/planning/`, only in a current plan; Installed shows one hint line per level, and a stale draft is never drawn). Everything goes through one `PlanEdit` function that sends the command with the draft's current revision, refreshes the plan and the planned topology (location and selection kept) and shows the saved toast; the server's refusal appears inline, in its words, without its "invalid plan command:" prefix.
- **Delete…** (inspector header and the Physical equipment page): an inline confirm with the preview computed once from the snapshot index: what goes (its ports or positions, bridges, cables) and the **circuits cut** (for each removed cable, the two active endpoints reached through passive continuity only, access end first, duplicates removed). Proposed equipment says its addition is dropped.
- **Disconnect** (a row action in the inspector's Ports/Positions table and in the Physical endpoint detail) names the circuit it cuts; **Connect…** on a free endpoint opens the patching screen (see "Patching screen" below; it replaced the M5a search box) and sends `add_cable`.
- **Containers:** Add site (Sites level), Add node (site screen), Add rack (node level, units 1–60, default 42) as small inline forms; proposed containers are dashed with PROPOSED; Delete on an empty container (installed or proposed), otherwise the hint "Delete is available once it is empty". Dragging a proposed node holds for the session only (the layout API knows installed nodes); a site that exists only in the plan has no layout fetch.
- **HDF form** (library drawer): name, rows 1–32, height, rack, lowest unit; it sends `add_hdf`, closes the drawer and opens the new HDF in Physical. A wide HDF face scrolls sideways with an always-visible scrollbar.
- **Library Add… forms** on the Access switch, Aggregation and Patch panel items (name, network for switches, rack, unit, ports or positions) send `add_equipment`; a drop from the library opens the matching form prefilled with the rack and unit, and an empty-canvas drop keeps the unplaced preview. Dragging is unchanged.
- **Keyboard and focus:** one hook, `useInlineDialog`, gives every inline confirm and form focus on open, Escape to close, and focus back on the button that opened it.

**Changes drawer** (`ChangesDrawer`). On **Installed**: the drafts ("current" or "Installed changed", with Open in Plan), New draft, and the recorded plans, read-only ("Recorded on <date> by <name> · <note>", with an expandable list of what each changed, built from the plan and its labels). In **Plan view**: a compact draft picker (drafts only; a stale one is marked "· behind Installed") with New draft, then for a current draft the grouped summary (Containers added, Equipment added, Moved, Removed, Cables connected, Cables disconnected; names only, each line linking to its object, each with **Undo** (`remove_change`; the toast says "also undid N dependent changes")) and **Record as installed…**. The **review step** calls `check` when it opens and lists any problem first (Record stays off while there is one), shows the grouped list and "Only record what is physically done.", requires a note (≤500) and Recorded by (≤100, prefilled from the last name used in this browser, `localStorage` in try/catch), and sends one record (the button is off while it runs; a 409 "already recorded" is shown as recorded, not as an error). After recording, the workspace switches to Installed with the same physical location, the remembered trace reruns, and the toast says how many other drafts now need Update draft. A **stale draft** shows the banner "Installed changed since this draft." with **Update draft**; on a 409 each conflict is listed with a link to the object (in Installed), the reason and **Drop** (`remove_change`); when none are left it says so and Update draft then succeeds. In Plan view a stale draft replaces the map and Physical with the **stale card** ("Installed changed since this draft": Update draft, Open Changes, View Installed). Recorded plans are never offered by the plan selector.

**Playwright projects.** `playwright.config.ts` has two projects. `main` runs every spec except `*.recording.spec.ts`. `recording` (`changes.recording.spec.ts`) has `dependencies: ['main']` and runs after it, one worker: recording a plan changes the shared test server's installed revision, which makes every other draft (the Expansion draft included) stale. Each recording spec builds its own drafts on the revision it finds (`e2e/plan-api.ts`) and only adds or removes what it made, so none depends on another's order. If a `main` test fails, `recording` does not run.

### Bulk data entry (M5c, complete)

M5c steps 7–9 are done; step 10 prepared the data-entry rehearsal, **which is pending the owner's run** (the procedure, the node to enter and the empty results tables are in [verification-guide.md](verification-guide.md) §6b; its time and friction list will be recorded here and in the plan when it has been run). Every bulk tool is an ordinary plan command or a `batch` of them, so recording stays the one path to installed (locked 10). Where each is opened and what limits it:

| Tool | Opened from | Limits |
| --- | --- | --- |
| `batch` | API only (the bulk tools send it) | 1–500 commands, all or nothing, one revision bump; no nesting and no `remove_change`; a command cannot refer to an object the same batch creates (IDs are the server's, returned in `ids`) |
| Connect a range | **Range** in the patching screen (**Connect a range…** in the Physical endpoint detail, Range in the jack popover) | up to 500 pairs; the near and far runs stay on one equipment side each; blocked pairs are skipped only when Skip is ticked |
| Duplicate | **Duplicate…** in the inspector header and on the Physical equipment page | 1–60 copies; same kind, role, network, height and size, never cables or details |
| Copy rack layout | **Copy rack layout…** on an empty rack card at the Physical node level | the target rack must be empty and not the source; every piece must fit the target's units; the box is positioned once when it opens and does not follow page scroll |

Undo is per change in the Changes drawer (there is no "undo the whole batch"), and a batch's changes are listed one by one there. `go run ./cmd/db seed -fixture empty` (also `cmd/testserver -fixture empty`) seeds an installed root with the three campus networks and nothing else, for the rehearsal. Details of each tool follow.

**`batch` command** (step 7). `{type: "batch", expectedRevision, batch: {commands}}` applies 1–500 of `add_equipment`, `add_hdf`, `add_cable`, `move_equipment`, `add_site|node|rack` and `delete_equipment|rack|node|site`, `disconnect_cable` in order, all or nothing, with one revision bump; no nesting and no `remove_change`; a command cannot refer to an object created earlier in the same batch (IDs are allocated by the server and returned as `ids`, one per command, `""` for commands that create nothing). A failing command makes the whole batch 422 with its position and the reason in names ("command 3 (add_cable): AGG-03 · Port 1 is already cabled (cable-a04)"); more than 500 or none is 422, a stale revision or recorded plan is 409. A batch equals the same commands run one by one (checked on 3,000 random batches); only `labels` can differ for objects a later command cancelled. A cable between two endpoints of the same equipment is refused by `add_cable` itself in names ("PANEL-A · 5 · Front and PANEL-A · 5 · Rear are on the same equipment"), alone or in a batch.

**Connect a range** (step 8; its inline box was replaced by the patching screen's Range mode, below). Count, the far start endpoint, then a list of numbered pairs with ✓ or ⚠ and the reason in names. Ordering is in the pure module `range.ts`: switch ports by port number, panel positions by position on the chosen side, HDF by row, then block A–D, then position 1–6, continuing into the next row; a pair past the last position (either side), on the same equipment, already cabled (with the cable ID) or reusing an endpoint of an earlier pair of the range is blocked, with the server's wording. While any pair is blocked **Connect** is disabled; ticking "Skip the N pairs that can’t be made" leaves them out. It sends one `batch` of `add_cable` through the one `PlanEdit` path (which now takes a batch) and shows a 422 in the box. Undo stays per cable in the Changes drawer. Switch ports have no `position`, so they run by the number in their label ("Port 7"), as a number.

**Duplicate and Copy rack layout** (step 9). Both are inline boxes in a plan, built on the pure module `duplicate.ts` and sent as one `batch` of `add_equipment`/`add_hdf` through `PlanEdit`; no server change. **Duplicate…** (`DuplicateEquipment.tsx`) sits in the inspector header and on the Physical equipment page, next to Delete…: "N more like <name>" (Count 1–60), a rack (the same one by default, or another in the trace picker's combobox), and a numbered preview "1  EDGE-19 · Rack A03 U7 ✓". Names count the trailing number up with its padding (EDGE-18 → EDGE-19, AGG-08 → AGG-09), skip names already in the proposed topology (any case), and add -2, -3… to a name without a number. Units are the next free positions where the height fits, going up from just above the original in the same rack and then wrapping to U1 (from U1 in another rack), so "no free unit" means the rack is full; a line with none says "Rack A03 has no free unit for EDGE-21". A copy takes kind, role, network, height and port count (a panel's positions; an HDF copies as `add_hdf` with the highest row of its blocks), never cables or details. **Duplicate N** is disabled while any line is blocked (change the count or the rack; there is no Skip). **Copy rack layout…** (`CopyRackLayout.tsx`) appears next to Delete on an empty rack card of the Physical node level and opens as a popover under its button: pick the source rack, see "U8  EDGE-17 → EDGE-18 ✓" for each piece of equipment at the same unit, then **Copy N**. It refuses the same rack, a target that is not empty and a source with nothing in it, and marks what does not fit a smaller rack in the server's words ("Rack Tiny has units 1–4; 1 unit from U8 does not fit"). Both show a 422's message in the box.

### Detail fields (M5b step 11)

Optional descriptive fields on the physical objects, as in the step 11 design: flat optional strings (camelCase, omitted when empty) on `Equipment` (`manufacturer`, `model`, `serialNumber`, `ipAddress`, `status`, `description`), `Endpoint` (`portType`, `connector`, `speed`, `state`, `description`), `Link` (cables only: `label`, `status`, `notes`), `Site` and `LocationNode` (`location`, `description`) and `Rack` (`location`, `rackType`, `description`). The structs stay comparable, so `Diff` still compares existing objects with `==` and still allows only a placement to change.

- **Validation** is in `topology.Validate`, so it holds for Installed and every proposed topology, with reasons in names (`SW1: status must be active, inactive or maintenance, not "broken"`, `SW1 · Port 2: state must be available, reserved, disabled or faulty, …`, `SN-0042 is already the serial number of AGG-03`): value sets (equipment status, port type, port state, cable status, rack type), 200 characters (1,000 for description and notes), `ipAddress` parses with `netip.ParseAddr` and is not unique, `serialNumber` is unique among filled values ignoring case, and a bridge carries no cable details.
- **Commands.** `add_equipment`, `add_hdf` (details of the HDF itself), `add_cable`, `add_site`, `add_node` and `add_rack` take an optional `details` object; values are trimmed, an unknown field name is 400, a field that does not apply to the object (`rackType` on equipment) is 422. **`update_details {target: {id}, details}`** sets or clears (an empty string) fields on an object **the plan adds**, including a proposed switch's ports; on an installed object it is 422 "Installed details are changed with a direct fix (M5b step 12), not in a plan". It is stored in the plan's `details` (one entry per object, later fields win), applied after the cables, named `update_details:<id>` by `Check` and the summary keys, undone by `remove_change`, dropped with its object, labelled like the other commands, and allowed in a `batch` (on an object created before the batch). Every command is also checked on its own, so a batch names the failing command ("command 2 (add_equipment): sn-9 is already the serial number of SW-A").
- **Migration `008_detail_fields.sql`** adds nullable text columns with `CHECK` constraints for the value sets and lengths, a check that bridges keep the cable columns empty, and a partial unique index on `lower(serial_number)`. It never fills a value. **It was applied to the development database on 2026-10-12.** `Seed` and `Record` write the fields; the installed snapshot and plans load them; `Diff` is unchanged.
- **A port's state is data (locked 6):** `faulty`, `disabled` or `reserved` ports and every other detail leave every trace unchanged (domain and HTTP tests).
- **Duplicate and Copy rack layout still copy no details** (the serial number least of all).
- **Not yet:** the inventory view (step 14). The Changes drawer does not list `update_details` entries yet, because nothing in the UI creates them.

### Interface names and mixed port types (M5b step 11b)

A switch is made with 1–8 **port groups** (`add_equipment.portGroups`), 1–96 ports in all (a plain switch may now have up to 96 ports too; a panel keeps 48 positions). Each group is `{count, names, start?, details?}`: `names` has exactly one `{n}` (`Gi1/0/{n}`), numbered from `start` (default 1, 0 allowed), and `details` are the `portType`, `connector` and `speed` every port of the group starts with; or `{labels, details?}` with the labels as they are (Duplicate sends groups this way, because a label is display text and is never parsed back into a pattern). Without groups a switch has one group "Port {n}". New ports get `position` 1…N in group order and `portGroup` 1…G; endpoint IDs stay `<equipment>:p<n>` and are never parsed. Labels are 1–64 characters and unique on the switch ignoring case; every refusal is in names ("SW-NEW: port group 2: Names must contain {n} once", `SW-NEW: port name "GI1/1" is used twice`, "SW-NEW: a switch has 1–96 ports, not 97"). Ports saved before 11b keep position 0 and group 0 and are ordered as before.

- **Validation and storage.** `Validate` allows a switch port a position ≥ 0 (unique per switch among positions > 0), no side and no subpanel, and a group only with a position. Migration 008 (edited in place; applied to the development database on 2026-10-12) relaxes the endpoint shape check, adds `port_group` and the unique index on `(equipment_id, position)` for switch ports with a position.
- **Order is stored, never parsed.** Only `side` tells a panel position from a switch port (a switch port now has a `position` too). Connect a range, the inspector's Ports table, the trace picker and the faceplate order a switch's ports by position (`shared/ports.ts`); the number at the end of a label is read only for ports with no position (saved before 11b).
- **Add form.** The Access switch and Aggregation **Add…** forms get **+ Add port group**: the plain Ports count becomes rows of Count, Names, Type, Connector (suggestions RJ45, LC, SC, ST, SFP, SFP+, QSFP) and Speed with a ✕, and one line says what the ports will be called ("28 ports: Gi1/0/1 … Gi1/0/24, Te1/1/1 … Te1/1/4"). Removing the last row returns to the plain count.
- **Faceplate.** One bank per group, side by side from left to right (access ports first, uplinks to their right) with a gap and a caption above each from its first and last label as they are, its type and speed ("Gi1/0/1–Gi1/0/24 · copper · 1G"), odd jacks above even ones; the faceplate uses the face card's full width, and what does not fit wraps to the next row (about 15 jack columns per row; a group of more than 24 ports is cut into blocks of 24 so it can wrap, with its caption on the first block). A switch with one group, or saved before groups, is one compact strip as before. Arrow keys follow what is seen (left to right, then the next row of banks; `layoutPlate` in `faces.ts` is shared by the drawing and `faceNav`). A jack is numbered within its bank and named by its label in the tooltip.
- **Copies.** Duplicate and Copy rack layout copy the groups (labels, order, portType, connector, speed) and never a serial number, IP address, status, description, port state or notes.
- **Error wording (step 11 review).** Detail messages say "IP address", "serial number", "port type" and "rack type", never the JSON names.
- A single port can be renamed with a direct fix (step 12; Edit port details in Physical since step 13). Not yet: saved switch models, bulk rename.

### Direct fixes and change log (M5b step 12)

- **Endpoints.** `PATCH /api/installed/{kind}/{id}` (`kind` is `equipment`, `endpoints`, `links`, `sites`, `nodes` or `racks`) with `{name?, details?, note?}` answers `{changes: Entry[]}`. `GET /api/change-log?entityKind=&entityId=` lists one object's fixes, newest first. The design said `?entityId=` alone; the query needs the kind as well so it uses the existing index `change_log_entity (entity_kind, entity_id, at)` without a new migration.
- **Fixable fields.** Equipment: `name` and the six details. Endpoint: `name` (a switch port's label, only a port with a position) and the port details. Cable: `label`, `status`, `notes` (no name; a bridge has no details). Site and node: `name`, `location`, `description`. Rack: `name`, `location`, `rackType`, `description`.
- **Name rules.** As the plan commands: trimmed; equipment, site, node and rack names 1–100 characters, a port label 1–64; equipment unique in Installed and sites unique, nodes within their site, racks within their node, port labels on their switch, all ignoring case. A duplicate serial number is refused in names before the database index.
- **Status codes.** 400 malformed JSON or an unknown field; 404 unknown object or kind; 409 duplicate name; 422 invalid value, a detail that does not apply, a topology field (`rackId`, `unit`, `networkId`, `role`, … "changes the topology: use a plan") or a note over 500 characters. Nothing is written on a failure.
- **Never topology.** A fix writes only that object's row and one `change_log` row per changed field (`note` optional), in one transaction, and **never changes the topology revision**, so drafts stay current and pinned traces stay valid. A fix that changes nothing answers `changes: []` and writes no row. A fix locks the installed root `FOR UPDATE` like Record, so the two never interleave; a Record after a fix keeps the fixed name.
- **Tests.** FX-01 `persistence/fix_test.go` (with the clear-to-NULL, refused-writes-nothing and fix-then-Record cases); FX-02 and FX-03 `httpapi/fix_api_test.go`; the pure rules `fixes/fixes_test.go`; the client in `frontend/src/shared/api.test.ts`.
- **Known limits.** Names are checked against Installed only (a draft that adds equipment with the same name is not checked; plans do not check names at record time either). Ports saved before port positions (position 0) cannot be renamed. There is no UI yet (step 13). Change-log rows carry no user until M7.

### Frontend

React/TypeScript, TanStack Query, React Flow. The conceptual map lives in `frontend/src/features/map/`, the inspector in `frontend/src/features/inspector/`, the physical explorer in `frontend/src/features/physical/`, and the Manage networks drawer in `frontend/src/features/networks/`; `App.tsx` only wires them in. Two libraries are loaded lazily, on the first export only: **`html-to-image`** and **`jspdf`** (separate chunks; the main chunk is about 528 kB).

**Shell.** The header (titled "Network Studio") holds the **Conceptual / Physical** switch, a **Show network** selector ("All networks", one network, and a last entry **Manage networks…**), and the **Installed / Plan** control. They are independent. Tools and drawers overlay the full-page map, and the map's results overlay and controls stay clear of whichever drawers are open. The view and network choice are not part of the URL.

**Conceptual map.** One card per equipment (each HDF is one card), one line per cable group.
- **First layout.** Deterministic and layered, with no new dependency: access switches in column 0, passive equipment in the column equal to its cable distance from an access switch, AGG/BB in the column after the last passive one, and equipment not reachable from an access switch parked in a row below. Columns are ordered by the average row of cabled neighbors, then name. Only cards without a recorded position are laid out; existing positions are never recomputed.
- **Session state.** `mapSession` (session-only, shared by Installed and Plan, never persisted) holds card positions by equipment ID, the viewport, pinned facets, the node/site highlight, the split cable pairs, the route-view state with its own viewport, and the pending center/fit requests. Dragging a card changes this map only (recorded at drag stop). The map fits once per session; refetches, saves, trace, filter and context changes never refit or reset it, and saving does not remount it. **Reset layout** (an inline confirm in the map controls) drops the recorded positions and the viewport, recomputes the first layout and fits once, and keeps pins, highlight, filter, split pairs and the trace. A reload starts again from the first layout.
- **Cards** show an icon, the name, the role (or PROPOSED), the site / node / rack, "N of M cabled" (device ports, or panel/HDF positions counted once), badges naming the networks of the circuits through a passive card (in the network's color), and their facets. There is no per-card button or popover. Clicking a card selects it and opens the inspector; a selected card keeps its size and is only raised in the stacking order. Cards with facets are raised above ordinary ones.
- **Cables.** Each network has one stable color from a small palette, by network order; an unresolved circuit is grey. Parallel cables between the same two cards that both attach to summary anchors and share a circuit network are **one line** in that color, 1.5 px plus 1 px per extra cable (at most 7 px); a single cable is a thin line. A line with two or more cables has a **count pill** at its midpoint, in the same color. Hovering the line or the pill shows a tooltip (a real element) listing the cable IDs. Clicking the pill or the line **splits** it into one line per cable, fanned out from the same two anchor points, each labeled with its cable ID; clicking a split line or its **join** control joins it again. Which pairs are split is kept in `mapSession` per card pair and network (`data-split-pairs`). The route's teal and the highlight's amber win over the network color, joined or split. Lines attached to facets stay one per cable. Proposed cables are dashed. Lines, bundles, and anchors are drawing aids and never feed traversal. A cable on another network than the filter is captioned with that network.
- **Network filter.** One network shows that network's active devices plus passive equipment carrying at least one of its circuits, and the cables between shown cards. A circuit's network is the network of its access device, computed by the same rule as the engine's passive start; an unresolved circuit has none. The filter is presentation only: it never changes what a trace finds.
- **Node and site highlight.** Clicking a site or node name in the **Explore** drawer (a highlighter icon shows on hover and keyboard focus) highlights every equipment located there, every cable leaving it, and the far-end cards of those cables (lighter amber); everything else fades to about 30%. The view fits the highlighted cards once, clear of the drawers. The highlighted part is shown even where the network filter would hide it. **Clear highlight** and Esc (outside text fields) clear it; another node replaces it. It is independent of the trace: route cards and lines stay teal and are never faded. The inspector's site and node links set the same highlight, and its rack link opens the rack in Physical. Choosing **equipment** in Explore (or Enter in its "Find equipment" search, which picks the first match) selects the card, opens the inspector and centers on the card, with no highlight.
- **Find AGG / BB.** Start from the inspector's **Find AGG / BB** (a switch, all ports), from a port or position row in the inspector, from a facet on a card, or from the Trace drawer. Exact port-to-port tracing stays in the Trace drawer. An expandable results overlay on the map lists every route, AGG first, with destination, role, network, and "N cables · M internal bridges", plus mismatches ("On another network (not routes)") and the truncation notice, with **Clear trace**. Selecting a route highlights its cables (teal, animated), reveals its automatic facets, and never moves a card or the viewport. The selected route expands to its **ordered hop list** (the start, then each CABLE or PANEL BRIDGE with its endpoint label and link ID); clicking a hop selects that equipment and centers the view on its card at the current zoom; a small **Show in Physical** icon on each hop (in both views) opens that endpoint in Physical. Centering and fitting keep clear of the open drawers, the results overlay and the tool rail, animate briefly, and are the only view moves besides the user's own pan, zoom and the first fit.
- **Trace drawer and picker.** The **Pathfinding** form (trace mode, Start, Destination) exists only in the Trace drawer. Start and Destination are searchable comboboxes over equipment ("EDGE-17 · all ports", in Find AGG / BB mode) and endpoints: words match in any order ("edge-17 3", "hdf-01 3c/5", "panel-a 1 rear"), at most 50 matches are shown with a "refine the search" note.
- **Facets** are exact endpoint detail on a card: one switch port, or one panel/HDF position with its front and rear endpoints and bridge ("3C / 5", with the parent HDF name always visible). *Automatic* facets come from the selected route, tagged "route"; they are replaced when the route changes and removed by Clear trace. *Manual* facets are tagged "pinned" and are made **only in the inspector** (the pin on a row). They survive route selection, route changes and Clear trace; a position that is both shows once with both tags. Clicking a facet starts Find AGG / BB from it.
- **Hidden route cards.** Cards on the selected route that the network filter or the highlight would hide are shown while the route is selected and hidden again when it is cleared. The backend result is always complete; display scope is not graph scope.
- **Library drops.** Dropping a library item on empty map space creates an unplaced, unsaved preview; its rack is chosen in the plan form. Drag-to-rack is not on the map: placement proposals go through the inspector's placement form (Overview tab, in a plan) and the rack level in Physical.

**Inspector** (`features/inspector/`). It opens when a card is selected or equipment is chosen in Explore.
- A **sticky header** stays visible while the content scrolls: icon, name, role, network and Installed/Proposed badges, the "N of M cabled" meter, the location breadcrumb (site and node highlight, the rack opens in Physical), **Show on map** (selects and centers the card), **Show in Physical** (opens the equipment page), and **Find AGG / BB** for switches only (a panel or HDF starts from one position).
- Two **tabs**, with arrow keys moving between them: **Overview** (role, placement, cabled counts per network, and the placement form in a plan) and **Ports** (**Positions** for panels and HDFs).
- The Ports/Positions tab is a **compact table**: label, far end, cable ID, network badge. A position shows front and rear as two lines in one row (an F/R marker; the far end's own Front/Rear suffix is in its tooltip). HDF positions are grouped under **collapsible subpanel rows**. A **Cabled / Free / All** filter (Cabled by default above 48 ports or positions) and a label search ("3C/5" and "3C / 5" alike) sit above it. Each row has three always-visible, small icon actions with tooltips: **Find AGG / BB from here**, **Show in Physical** (opens the equipment page with that endpoint selected; for a position, the first cabled side, else the front) and **Pin / Unpin on map**. Clicking a row selects it. Network badges use the same colors as the map. Per-snapshot lookups (`snapshotIndex`) back every row; nothing scans all links.

**Route view and export.** A **Route view** toggle sits in the results overlay, above the hop list of the active route. While it is on, the canvas shows only the active route's cards and cables, laid out left to right in hop order by a pure function (`routeView.ts`: one card per equipment in order of first appearance, with the route's exact positions as facets), not by the layered layout. Pins, the highlight, the network filter and split pairs do not apply there. Dashed rounded **node boxes** sit behind each run of consecutive cards in the same node, labeled "Site / Node" (grouping by location ID, never by name; a route that leaves a node and returns gets a second box); a lighter dashed **rack box** nests inside it only where two or more consecutive cards share a rack. The boxes are drawing aids: they are never an input to a trace. Entering fits the route and its boxes once, clear of the drawers, the overlay and the tool rail; the route view keeps its own viewport and card drags stay local. Turning it off restores the full map exactly (positions, pins, highlight, filter, split pairs, viewport). Clearing the trace turns it off.
- **Export.** **PNG** and **PDF** buttons next to the toggle are enabled only while the route view is on (otherwise disabled with a title saying why; absent without an active route). One client-side capture of the route view's React Flow viewport at pixel ratio 2 (lowered so no side passes 8000 px), fitted to the cards and boxes with padding, under a header band drawn into the image: start → end, the mode, the network, "Installed" or "Proposed: <plan name>", and the date. The PNG downloads as `route-<start>-<end>.png`. The PDF is one page sized to the image, the image deflated (about 180 KB for the acceptance route), with an invisible ASCII text layer carrying the header. The capture is of a clone, so the on-screen view, the session and the snapshot are not touched, and no backend call is made.

**M3.2 fixes.**

The results overlay's title is "Find AGG / BB" or "Exact port → port" according to the search.
- Choosing another route while the route view is on lays the new route out afresh from the route-view model (a dragged card does not keep its place) and fits it once, clear of the drawers; a refetch of the same route is not a new route.

**Physical** (`features/physical/`). Sites → site → node → rack → equipment, with breadcrumbs. It always shows the **complete physical inventory**: a one-line scope note under the breadcrumbs says so ("Complete physical inventory. All networks are shown." or "… Network A selected: its devices are marked; other networks stay visible."). The chosen network and the selected route only mark things: active devices of other networks are muted (never hidden), and the route's equipment, racks, nodes and sites are teal. The header's **Physical** switch opens the current physical location (Sites the first time). The explorer's root carries the model as data marks (`data-physical-level`, `data-location`, `data-history-depth`, `data-route-equipment`, `data-node-positions`, `data-site-fitted`, `data-shown-racks`, `data-rack-equipment`, `data-rack-free-units`, `data-selected-equipment`, `data-selected-endpoint`, `data-side`, `data-face-kind`, `data-face-blocks`, `data-face-positions`), which the specs assert.
- **Sites.** A card grid, sorted by name: a "SITE" label, the name, "N nodes · N racks · N equipment", outlined network badges in the map's colors ("Network A · 5 active"), and, when the selected route touches the site, a teal "on route · N equipment" pill and a 2 px teal border. No coordinates and no lines between sites.
- **Site.** Only the site's node cards (no site card), on a dot-grid canvas. **Cards are dragged freely**; the position is **saved on the server once at drag stop** (`PUT`), with an optimistic cache update that is rolled back, with an error toast, if the save fails. Nothing is sent while dragging. A node with no saved position gets a default: up to 12 go on a ring in name order (clockwise from the top, a radius where no cards overlap and no line crosses a third card), more than 12 in a grid, either way below the saved nodes. Unsaved cards keep their on-screen position when another card is dropped. A card shows "N racks · N equipment", its network mix, "N cables inside", "N cables to <site>" (a link that opens the list of those cables) and **Open racks →**. **Lines** join each pair of nodes that have cables between them, counted from real cable records through equipment → rack → node (never from names): 3–8 px by count, in the network's color (grey when the cables mix networks, teal when one is on the selected route, dashed in a plan when all its cables are proposed), with a filled count circle at the midpoint. Hovering lists the cable IDs; clicking opens a **cable list** (each cable with both ends and their racks); a row's end opens that endpoint on the equipment page. The lines are a summary and never feed traversal. A small note panel says "Lines are cables between nodes, counted from real cable records. Positions are your arrangement, not a floor plan." **Reset layout** (inline confirm) deletes the site's saved positions and refits. The screen **fits into the visible part of the canvas**, clear of the open drawers, the results overlay and the tool rail, once per site per session and again after Reset layout; it stays hidden until that fit is done (`data-site-fitted`), and a site left earlier in the session reopens at its remembered viewport.
- **Node.** Only the node's own racks, as 200 px previews: name, "N equipment · N of 12U used", "N proposed" when a plan adds equipment, a teal "on route" pill and border for racks the route uses, and a dark mini elevation with one block per equipment spanning its height (a colored left edge for active devices, dashed for proposed ones, quieter for other networks). A search box over rack and equipment names appears above 12 racks. A click on a block opens that equipment's page; a click elsewhere on a preview opens the rack. In a plan, previews accept the same drops as a free unit (library items, and equipment dragged from another rack of the node).
- **Rack.** The full elevation of one rack, top unit first: unit labels "U12…U1", free units marked "Available", and one block per equipment spanning its height (a 3U HDF at U4 is one object over U4–U6) with a bold name and "role · Network A · 3U at U4–U6". Route equipment is teal, the selected equipment is ringed amber, proposed equipment is dashed with a PROPOSED tag, other networks' equipment is muted. In a plan, free units accept drops from the library or from existing equipment, with the same `rack-slot-<rack>-<unit>` test IDs and the same move/create handlers as before (a multi-unit block carries the ID of its lowest unit). Moves to other nodes use the inspector's placement form. A click on a block opens the equipment page.
- **Equipment page.** Left, a 150 px strip of the rack with this equipment ringed (a click on another navigates); center, the face; right, the endpoint detail. The face is a switch's port bank (40 px buttons in rows of 12), a panel's positions 1..N on the chosen side, or an HDF's grid (columns A–D, the configured rows, six positions per block in a 3 × 2 layout, the block labeled "3C"). A **Front | Rear** control for panels and HDFs keeps the position and selects its other-side endpoint through the per-snapshot bridge lookup. Every endpoint is a real button named like "HDF-01 3C / 5 rear, cabled, Network A, on selected route". Fill follows state, never the network ID: free is white (even if its position carries a circuit), cabled uses the circuit network's color, on the route is teal, and the selected one has a dark ring; a block with a route position has a teal border. Other networks' positions are always drawn. The **endpoint detail** shows the label, side, circuit network, the fiber pair as secondary text (HDF only), the **external cable** (cable ID, far endpoint, far equipment and its "Site / Node / Rack", **Go to peer**), the **internal peer** for panel and HDF positions (the other side, its cable, **Switch to front/rear**), **Find AGG / BB from here** (it stays on the page; the routes show in the results overlay) and **Show on map**.
- **Breadcrumbs and Back.** Clickable breadcrumbs and an in-app **Back** over a session-only history. Navigating, a breadcrumb and **Go to peer** push; selecting an endpoint and switching sides replace the location without a history entry; Back restores the exact location, endpoint and side. There is no router and nothing in the URL; a reload starts at Sites.
- **Explore in Physical.** While Physical is shown, the Explore drawer navigates it: a site or node name opens that screen, a rack opens its elevation, equipment opens its page (the inspector is not opened). In Conceptual it keeps its map behavior.
- **Results in Physical.** The same results overlay as the map, without the Route view toggle and export. A hop row opens that endpoint on the equipment page; selecting another route changes the marks and never navigates; Clear trace removes the marks only.
- **Show in Physical.** The inspector header and its Ports/Positions rows, and an icon on every hop of the results overlay (both views), open the equipment page, with the endpoint and side selected when given.
- **Switching views and contexts.** **Conceptual** shows the map exactly as it was (the same route, card positions and viewport, no automatic centering); the selected equipment is shared, so the inspector shows the last physical equipment. The **Installed / Plan** switch keeps the physical location and, where the place does not exist in the other context (EDGE-18 is only in the plan), falls back to the nearest one that does (its rack) instead of Sites. The physical state lives in `physicalSession` outside the Workspace.
- **Pure modules** (`features/physical/`, unit-tested): `location` (`resolveLocation` with fallback), `history` (navigate, replace, back, breadcrumbs), `physicalSession`, `inventory` (counts per site/node/rack and route marks, one pass per snapshot), `connections` (cables between nodes, inside a node, to other sites), `layout` (the default arrangement), `elevation`, `faces`, `detail` (external peer, internal peer, side switch), `explorerModel` (mixes, scope note, location marks, rack previews, cable rows, saved-position updates, `openLocation`), `equipmentModel` (cell look, accessible names, face meta, detail model), `drops`, plus the components.

## Known limits

- **Nothing from the conceptual map is persisted to the server.** Card positions, the viewport, pinned facets, split pairs, the highlight, the route view, and the network choice are browser-session state and are lost on reload. Only the Physical site screen's node positions are saved.
- **The full snapshot is loaded on the client, and the default map draws every card and cable.** Highlight, route view, and summaries are client-side; bounded neighborhoods, large-network scoping and measured performance are deferred to M6. Measured: 1,700 equipment and 36,000 cables project in about 30 ms, but on the campus fixture **the first map render takes 3.6 s** (development machine, dev server; see the campus timings above). That is M6 work, to be measured on real data before go-live. The route view turns React Flow's culling off (it has few cards, and all must be measured to be fitted).
- **Cards can still overlap.** The first layout spaces cards 200 px apart vertically, so a card that grows (pinned or route facets) can cover the one below it; selecting a card no longer changes its size. There is no automatic re-layout.
- **Split lines share their end points.** A split pair's lines fan out from the same two anchor points, so they overlap near the cards; their middles and labels are apart. Different networks' lines between the same two cards also share a midpoint.
- **Export is a still picture.** The route's animated dashes come out solid, the header is drawn into the image (so it is not text in the PNG), the PDF's text layer is ASCII only ("->" for the arrow), and nothing is exported larger than 8000 px on a side (the pixel ratio drops instead). Exporting needs the route view on and a route that has drawn cards.
- **`hdf-display` flake.** One full Playwright run during M3 step 5 failed `hdf-display.spec.ts`; it was never reproduced (0 of 40 runs alone, 12 isolated repeats earlier). The inferred cause is that a new proposed, unconnected HDF is parked in the layout's bottom row, outside the fitted view, so whether React Flow had drawn it depended on timing. The spec now asserts the card through the projection (`data-cards`) and brings it into view through Explore before checking its icon. The cause is inferred, not observed, and no failure has been seen since.
- **Half-valid stored plans return 500.** An overlay that fails validation (for example, a stored plan with an HDF chassis but no grid) is refused, but `repositoryError` maps the plain validation error to a generic 500 "Database operation failed". Plans created through the API cannot reach this state.
- **Large drafts.** `GET /api/plans` returns full drafts, so a plan with a 32-row HDF carries about 2,400 additional records per plan listed. Pagination and scoped summaries are M6.

- **Physical node positions are shared, last write wins, and unprotected.** Everyone sees the same arrangement, two people moving the same node simply end where it was last dropped, there is no revision check or undo, and there are no permissions until M7 (anyone can also create and rename networks).
- **Physical history is lost on reload.** The location, Back history, the fitted/viewport state of each site screen and the explorer's search text are session-only; a reload starts at Sites.
- **Unsaved nodes re-flow after a reload.** In a session, dropping one node does not move the others, but a node with no saved position is placed by the default arrangement (below the saved ones), so unsaved cards can land somewhere else on the next visit.
- **A line's pill can land on a third card** when saved positions put a card on the line between two others; it stays clickable above the cards.
- **Two one-off Playwright failures (PHY-10, POL-02).** Each failed once during a review run, while the reviewer had started a second test server at the same time. Neither reproduced (50 and 15 repeats), and no failure has been seen with only one server running.
- **The conceptual map of a campus-size network is one tall, thin column of tiny cards** (its first layout stacks the access switches); readable only after zooming. The first render is 3.6 s. Both are M6.
- **The Trace drawer and Explore still take about 0.3 s and 0.8 s to open on the campus.** The time is the browser laying out the 1,541-card map and Explore's 1,500-row tree, not application code.
